BP-tree ordered-scan optimization and fresh-put retuning, 2026-10-09
================================================================

Environment: Go 1.26.4, Linux amd64, AMD Ryzen Threadripper 3960X.
Scan baseline: de70087, already using compact records and void Put/Del.
Final defaults: Fanout=256, LogSize=42, NumBlocks=32, BlockSize=34.
Earlier defaults: Fanout=64, LogSize=32, NumBlocks=32, BlockSize=32.
Competitors: tidwall/btree v1.8.1 and glycerine/rbtree v0.2.2.

Implementation
--------------
Scan, Range, and All now visit contiguous runs rather than driving the merge
cursor once per record. The reserved first slot of each block mirrors its
header, making a sorted block plus its boundary record contiguous. This uses
existing spare slots, not a separate scan array. All header overwrites,
deletions, and loads synchronize the mirror, including pointer-value clearing.
Explicit iterators retain their own cursor implementation.

The run cursor resolves buffered shadows and tombstones at run boundaries;
an empty log takes a separate fast path. After a leaf has been scanned before,
a later long scan may flush its log to avoid repeated merging. First visits
and narrow ranges retain lazy merging. Scratch-capacity checks avoid allocating
on scans of tiny trees. Scan-driven physical movement increments the tree
version. Every callback checks for mutation before touching borrowed storage
again, including mutations caused by nested scans. Len remains exact.

After the first parameter sweep, separator storage was changed to grow
geometrically instead of allocating an exact-size array on each internal-node
growth. Refresh clears only removed separators, not entries about to be
overwritten. A string-key regression test checks clearing and regrowth.
No production unsafe, assembly, or architecture-specific implementation.

Dict and its iterator, examples, and active benchmark rows were removed at the
user's request. Tree tests formerly sharing dict_test.go were retained in
maprange_test.go and other Tree tests. Historical benchmark artifacts are left
intact. Deleted code remains recoverable from Git history. make bench now
measures 22 distinct cases instead of 29.

65,536 uint64 key/value entries. Do not compare these pinned timings directly
with the unpinned README tables or earlier unpinned results.

Parameter sweep and selection
-----------------------------
237 unique configurations across successive geometry, refinement,
neighborhood, finalist, second-leg and confirmation rounds. Discovery covered
internal fanout, log size, block count and block size, including non-powers of
two. Early rounds use fewer timed operations; do not rank their absolute times
against later rounds. Raw samples and all configurations are preserved.

Finalists use two fresh-key patterns: the README odd/even adjacency trace and
independent disjoint even keys from the same permutation. Each is measured
at 65,536 and 1,048,576 initially loaded keys. Rank by equal-weight geometric
mean of the FOUR median ns/Put values. Scans do not contribute to selection,
honoring the user's explicit priority for fresh puts.

Before the separator change, f256-l32-h32-b34 ranked first among 18 finalists
(score 155.93 versus 163.21 for f64-l32-h32-b32). Separator growth reduced
large-load medians from 192.2/212.0 to 188.8/209.0; small-load results were
roughly flat, 106.8/132.3 versus 107.4/133.6. Allocation traffic fell by about
1 B/Put in the independent and large cases. See refresh-*.txt.

The 33-configuration second-leg sweep found f256-l40-h32-b34 best, score
152.75 versus 154.21 for its 32-entry-log counterpart. A final nine-config
confirmation explored nearby logs and fanouts with FIVE samples of 1,048,576
timed inserts per workload:

Configuration          Small adjacent  Small independent  Large adjacent  Large independent  Score
f256-l42-h32-b34                109.6              135.9           185.5              203.4  153.97
f256-l46-h32-b34                111.2              138.3           181.3              202.1  154.07
f256-l44-h32-b34                110.4              138.2           183.2              204.1  154.55
f256-l32-h32-b34                108.4              134.4           188.7              208.1  154.66
f256-l40-h32-b34                109.3              136.0           188.2              208.8  155.46

Adopt the best observed configuration even though its additional 0.4% over
the intermediate 32-entry log, and 0.07% over the runner-up, are NOT
statistically established advantages. Rankings vary across runs. This is a
measured workload-specific choice, not proof of a globally optimal geometry.

Memory
------
At fixed geometry, the scan changes do not increase retained heap:
2,474,184 bytes at 100,000 entries, unchanged from the compact-record version.
The final write-focused defaults use 2,560,376 bytes (25.60 B/key), +3.5%.
That remains 29% below the original 3,609,800 bytes (36.10 B/key). Tidwall
retains 2,513,408 bytes (25.13 B/key). Go map: 2,364,576; rbtree: 6,400,080.

Final leaf record array: 1,162 * 16 = 18,592 bytes, plus two bitmap words
(16 bytes), excluding metadata. Live leaf capacity is 1,088 keys. The larger
log crosses a Go allocation-size boundary; nominal array bytes are not
retained heap bytes. Shared redistribution scratch capacity is 17 KiB for
uint64 pairs. Isolated post-GC measurements include metadata and tree buffers.

Validation
----------
go test -count=1: PASS
go test -race -count=1: PASS
go -C bench test -count=1: PASS
go -C bench test -race -count=1: PASS

Coverage includes randomized map/scan models, balanced splits/merges/root
collapse, header mirror overwrites/deletion/resurrection, pointer clearing,
NaNs, bitmap word boundaries, exact deferred counts, live callback mutation,
nested scan preparation with retained iterators, and zero-allocation queries.
Two fixtures assumed a 32-entry log; they now establish their intended log
state independently of the default size. No current Go source or README
references the removed Dict API.

Reproduction
------------
Build once: go -C bench test -c -o /tmp/bufftree-scan-tuned.test
Run these serially to avoid benchmark interference:

taskset -c 6 /tmp/bufftree-scan-tuned.test -test.run='^$' \
  -test.bench='^BenchmarkCompareIteration$/^(Tree|Tidwall)$/^Scan' \
  -test.benchtime=500ms -test.count=5 -test.cpu=1
taskset -c 6 /tmp/bufftree-scan-tuned.test -test.run='^$' \
  -test.bench='^BenchmarkFreshPut$/^(Tree|Tidwall)$' \
  -test.benchtime=1048576x -test.count=5 -test.cpu=1
taskset -c 6 /tmp/bufftree-scan-tuned.test -test.run='^$' \
  -test.bench='^BenchmarkTuneConfirm$/./^Fresh' \
  -test.benchtime=1048576x -test.count=5 -test.cpu=1

Prefix with BUFFTREE_BENCH_N=1048576 for large-load checks. The mixed and
native-full-traversal benchmarks use -test.benchtime=300ms -test.count=3;
BenchmarkScanFirst uses -test.benchtime=64x -test.count=3. All use -test.cpu=1
and taskset -c 6. Memory: make memory. Unpinned tables:
make bench BENCH_TIME=250ms BENCH_COUNT=5

To reproduce intermediate geometries without changing defaults, use the
explicit configuration benchmarks in bench/tuning_bench_test.go. Baseline
comparisons require the old production sources at de70087. The cold/mixed/All
baseline harnesses were compiled with old bpa.go/tree.go via a Go overlay,
while other production code still had its old defaults.
